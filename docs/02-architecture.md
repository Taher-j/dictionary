# Architecture

## Stack

| Concern | Choice | Notes |
| --- | --- | --- |
| Framework | Expo (SDK 57 or newer stable), React Native | Development builds from day one. Do not target Expo Go. |
| Language | TypeScript, `strict: true` | No `any`. |
| Navigation | Expo Router, routes in `src/app` | Gives deep links. Do not install React Navigation packages. |
| Database | `expo-sqlite` | FTS5 is enabled by default. No SQLCipher. |
| Query layer | Drizzle ORM + drizzle-kit | Typed schema, generated migrations bundled and run at startup. |
| Data cache | TanStack Query | Wraps repository calls. Handles caching, invalidation, infinite lists. |
| UI state | Zustand | Active session, filters, sheets. Never database rows. |
| Scheduling | `ts-fsrs` (FSRS-6) | Imported only by `src/domain/scheduler.ts`. |
| Lists | `@shopify/flash-list` | For every list that can exceed ~50 rows. |
| Animation | Reanimated, Gesture Handler | Versions bundled with the Expo SDK. |
| Files | `expo-file-system`, `expo-document-picker`, `expo-sharing` | Wrapped in `src/services/files.ts`. |
| Spreadsheets (M6) | SheetJS from its tarball, vendored in `vendor/`; Papa Parse for CSV | **Never** install `xlsx` from the npm registry: that copy is frozen at 0.18.5. Install from `https://cdn.sheetjs.com/`. |
| Speech (M7) | `expo-speech` | Wrapped in `src/services/speech.ts`. |
| Notifications (M8) | `expo-notifications`, local scheduling only | Wrapped in `src/services/notifications.ts`. No push. |
| Share target (M9) | `expo-sharing` config plugin (receive side) | Android intent filter + iOS share extension. |
| i18n | `i18next`, `react-i18next`, `expo-localization` | English only for now; architecture ready for more. |
| Charts (M8) | `react-native-svg`, hand-drawn | No chart library. |
| Tests | Jest (domain + repositories), Maestro (E2E, from M10) | Repository tests run in Node with `better-sqlite3` and the same Drizzle schema. |

Package manager is pnpm. Install Expo packages with `pnpm expo install <pkg>` so versions match the SDK.
Dependencies not in this table need approval first.

## Layers

```
src/app        routes only (Expo Router)
   |
src/features   UI + hooks per feature
   |
   +--> src/domain    pure TypeScript: models, scheduler, session, importing, backup
   +--> src/data      repositories, Drizzle schema, migrations   (returns domain models)
   +--> src/services  thin wrappers over device modules
   +--> src/ui        design-system components and tokens
```

`src/data` may import types and helpers from `src/domain`. `src/domain` imports nothing from the
other layers.

## Patterns

### Repository

One interface per aggregate, one SQLite implementation. Repositories return domain models,
never Drizzle row types.

```ts
// src/data/repositories/wordRepository.ts
export interface WordRepository {
  getById(id: WordId): Promise<Word | null>;
  list(query: WordQuery, cursor?: WordCursor): Promise<Page<WordListItem>>;
  search(text: string, query?: WordQuery): Promise<WordListItem[]>;
  findDuplicates(dictionaryId: DictionaryId, keys: TermKeys): Promise<DuplicateMatch[]>;
  create(input: NewWord): Promise<Word>;
  update(id: WordId, patch: WordPatch): Promise<Word>;
  softDelete(ids: readonly WordId[]): Promise<void>;
  restore(ids: readonly WordId[]): Promise<void>;
}
```

`WordQuery` is one filter object (dictionary, tags, status, starred, incomplete, sort) shared by
lists, search, free practice and export.

All repositories are created once at startup and provided through `RepositoriesProvider`.
No dependency-injection framework.

### Feature hooks

```ts
// src/features/words/hooks/useCreateWord.ts
import { useMutation, useQueryClient } from '@tanstack/react-query';
import { useRepositories } from '@/data/RepositoriesProvider';
import { dictionaryKeys, wordKeys } from '@/data/queryKeys';
import type { NewWord } from '@/domain/models';

export function useCreateWord() {
  const { words } = useRepositories();
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: (input: NewWord) => words.create(input),
    onSuccess: (word) => {
      void queryClient.invalidateQueries({ queryKey: wordKeys.lists() });
      void queryClient.invalidateQueries({ queryKey: dictionaryKeys.detail(word.dictionaryId) });
    },
  });
}
```

Query keys live in `src/data/queryKeys.ts` as factories (`wordKeys.all`, `.lists()`, `.list(query)`,
`.detail(id)`). Long lists use `useInfiniteQuery` with keyset cursors.

### Practice engine

A mode is an object with three functions; the session is a pure reducer. The React screen only
dispatches events and renders the current question.

```ts
// src/domain/session/types.ts
export type ModeId = 'flashcard' | 'typed' | 'choice';

export interface Question {
  cardId: CardId;
  mode: ModeId;
  prompt: string;
  answer: string;
  options?: readonly string[];
}

export interface PracticeMode<TResponse> {
  id: ModeId;
  canAsk(card: Card, word: Word, ctx: SessionContext): boolean;
  build(card: Card, word: Word, ctx: SessionContext): Question;
  grade(question: Question, response: TResponse): Rating;
}

export type SessionEvent =
  | { type: 'answered'; cardId: CardId; rating: Rating; at: number }
  | { type: 'undone' }
  | { type: 'skipped'; cardId: CardId };

export declare function sessionReducer(state: SessionState, event: SessionEvent): SessionState;
```

Only the flashcard mode exists in the MVP. Later modes are added as new `PracticeMode` objects
plus one renderer component; the queue, scheduler and summary do not change.

### State

| Kind of state | Lives in |
| --- | --- |
| Words, dictionaries, tags, cards, logs, settings | SQLite, read through TanStack Query |
| Active review session (queue, index, revealed) | Zustand store wrapping `sessionReducer` |
| Search text, filter selections, open sheets | Zustand or component state |
| Theme, locale | Derived from system + `settings` table |

## Testing

- **Domain**: Jest unit tests for everything in `src/domain`. Target: scheduler, study day,
  term keys, duplicates, queue building, session reducer, mode grading, import planning, backup
  round-trip.
- **Repositories**: Jest in Node against `better-sqlite3` using the same Drizzle schema and
  migrations.
- **Migrations**: one fixture database per released schema version, migrated to latest in a test.
- **E2E**: Maestro flows from Milestone 10 (add word, review, backup/restore, import).
- UI components are not unit-tested unless they contain logic.

## Performance rules

- A seed script creates 50,000 words and 200,000 review logs for manual performance checks.
- Lists: FlashList + keyset pagination on `(term_fold, id)`.
- Bulk writes: transactions of about 500 rows with prepared statements.
- Search starts with `LIKE`; FTS5 is added only if the measurement in Milestone 1 demands it.
  See `03-data-model.md`.

## Future-proofing conventions (adopted, enforce from Milestone 0)

| Area | Convention now | Do not build yet |
| --- | --- | --- |
| Cloud sync | UUID ids, `updated_at`, `deleted_at`, append-only review log, repositories as the only DB access | Operation logs, server, accounts |
| Share-to-app | `/add?term=&context=` is the single entry for external capture; bundle id and URL scheme fixed in M0 | The share extension (M9) |
| Localisation | `t()` everywhere, `Intl` formatting, logical style properties | Translations, RTL testing |
| Monetisation | `Screen` owns safe areas and has an optional footer slot; no screen assumes it controls the bottom edge | SDKs, entitlements, flags |
| Notifications | All scheduling behind `src/services/notifications.ts` | Push, tokens, servers |
| Analytics | Nothing | Any wrapper, even a no-op |
| Public release | Final bundle id and app name early; versioned backups; migration tests; licence check | Store assets |

Lint rules to set up in Milestone 0:

- no hard-coded UI strings in JSX
- no `marginLeft/Right`, `paddingLeft/Right`, `left/right`, `textAlign: 'left' | 'right'` in styles
- import boundaries: `drizzle-orm` / `expo-sqlite` only under `src/data`; `ts-fsrs` only in
  `src/domain/scheduler.ts`; nothing under `src/domain` may import `react`, `react-native` or `expo-*`
